## 4. HEALTH CHECK — why it passed despite DB failures
Pipeline `health_check` for this deployment probes:
- **K8s readiness/startup probe** → `GET /health` on the pod (one 503 during boot before uvicorn bound, then became Ready).
- **`GET /` (frontend)** → **SKIPPED** (frontend_type = cloudflare, served from R2).
- **`GET /health` (backend)** → FastAPI returns **404 Not Found** (route not defined). 404 is **non-5xx**, which the health gate treats as "server is up" → **PASS**.
It passed because the gate only checks `/health` (which returns a non-5xx 404) and never exercises any DB-backed `/api/*` endpoint. So an unreachable Postgres cannot fail this gate. `/health` returning 404 also means the health endpoint is not DB-aware.

---
## ROOT CAUSE
The production image runs with **APP_ENV=dev**, so the app boots in dev mode (AUTH STUB) and points its Postgres/SQLAlchemy connection at **localhost:5432**, which does not exist in the production pod → `connection refused`. There is no production Postgres URL configured (only DEV_/STAGING_ DATABASE_URL names), and the Emergent platform only provisions MongoDB — not Postgres. DB-backed functionality therefore cannot work in production. The pipeline health gate does not catch it because it only checks a non-DB `/health` (which returns non-5xx 404).

## SUGGESTED FIXES (not applied — report only)
1. **User (Secrets):** Set `APP_ENV` to the production value and provide a real production relational DB URL pointing at a reachable host (not localhost:5432). Today only DEV_/STAGING_ DATABASE_URL names exist.
2. **User (external service):** Provision an externally reachable Postgres instance — Emergent provisions MongoDB only, so Postgres must be hosted outside the platform — and point the production DATABASE_URL at it.
3. **Code (E1):** Stop defaulting to `env=dev` + localhost Postgres + AUTH STUB in production; select the production DB host/auth from env, and make `/health` DB-aware (currently 404) so health_check can surface DB outages.
